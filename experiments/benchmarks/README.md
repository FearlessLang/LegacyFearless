# FeaRT benchmark report

This directory measures the FeaRT (Zig) backend for Fearless against two
baselines:

- the same FeaRT program with VPF automatic parallelism removed; and
- the original Java backend.

The primary question is whether VPF makes automatically parallel programs faster
than their sequential elisions. The Java backend is included to show the current
end-to-end performance gap, not as a normalized compiler comparison: it often
executes a different amount of parallel work.

Measurements in this report were taken on 2026-08-17 on a Ryzen 9 9950X (16
physical cores, 32 logical cores), with the CPU governor set to `performance`
and no competing workload.

## Summary

VPF substantially improves the five workloads whose computation reaches a
parallel driver: 4.2x for `primes` and 11.9x--16.5x for the divide-and-conquer
benchmarks. The four divide-and-conquer workloads use 24--27 cores on average.

FeaRT's sequential elision is still 10.7x--61.0x slower than Java on the four
shared divide-and-conquer workloads. The direct `java/feart` column is therefore
not evidence of a better scalar backend: on those workloads FeaRT uses roughly
26 cores while Java is effectively sequential.

`wc` and `grep` intentionally execute their user-supplied folds sequentially.
VPF consequently provides no speedup for them, and Java is about three times
faster on the current 1 MiB corpus.

## Configurations

| Configuration | Compiler flags | Purpose |
|---|---|---|
| `feart` | `--feart` | FeaRT with VPF automatic parallelism enabled. |
| `feart-novpf` | `--feart --no-vpf` | Sequential elision: the same source with all VPF machinery compiled out. The binary carries no locals structs, retain/drop hooks, thief functions, frame pushes, or compiler fences, so this column is the genuine scalar baseline. |
| `java` | *(none)* | Original Java backend. |

The configurations are allowed to use all logical cores. This is the operating
mode the backends select by default; this report does not include a thread-count
sweep.

The sequential-elision design follows Westrick et al., *Automatic Parallelism
Management* (POPL'24). It isolates the effect of automatic parallelism without
requiring a second, manually sequential version of every benchmark.

## Method

Each benchmark is built before timing. The timed command launches only the
generated executable: a native binary for FeaRT and `base.FearlessMain` for the
Java backend. Compilation is excluded; process startup is included.

For every benchmark and configuration, `run.sh` first runs the program once and
compares its output with the `feart` result. A mismatch aborts the sweep. It
then uses `hyperfine` with three warmup launches and at least ten measured
launches. The table reports the arithmetic mean of the wall-clock samples.

The raw `hyperfine` exports live in `results/`. `report.py` regenerates the
table from those files.

The derived columns are:

| Column | Calculation | Interpretation |
|---|---|---|
| `overhead` | `feart / feart-novpf` | Below 1 means VPF reduced elapsed time; above 1 means it increased elapsed time. |
| `speedup` | `feart-novpf / feart` | The inverse of `overhead`; above 1 means VPF improved elapsed time. |
| `java/feart` | `java / feart` | Above 1 means FeaRT finished sooner, subject to the parallelism caveat below. |

Geometric means summarize ratios only. They do not summarize absolute time.

## Workloads

Every workload is a self-contained Fearless project with `bench.Test` as its
entry point. Each prints a deterministic checksum.

| Benchmark | Workload | Checksum | Purpose |
|---|---|---|---|
| `mapLight` | 1,400,000,000 elements | `1960000000000000000` | Divide and conquer with one trivial operation per leaf. This is the finest-grained VPF case. |
| `mapHeavy` | 1,500,000 elements, 1000 mixing rounds | `8149048745584505931` | The same divide-and-conquer shape with expensive element work. |
| `mandelbrot` | 2048 x 2048 pixels, at most 256 iterations | `252714035` | Escape-time calculation with irregular per-pixel work. |
| `nqueens` | 14 queens | `365596` | Deep irregular search. |
| `primes` | Trial division through 1,000,000 | `78498` | A flow pipeline whose terminal drives splitting. |
| `wc` | 1 MiB generated corpus | `1048629 15009 164764` | Word, line, and byte counts over `Str.codepoints`. |
| `grep` | 1 MiB generated corpus | `21` | Literal `needle` matching over `Str.codepoints`. |

The workloads use direct functional Fearless and do not specify manual
granularity thresholds. Divide-and-conquer recursions run to single-element
leaves; the runtime chooses where to promote work. Several checksums have
independent references: `mapLight` is `n^2`, `primes` is
`pi(10^6) = 78498`, and `nqueens` is the known 14-queens count.

### Corpus

`wc` and `grep` use `corpus/corpus.txt`, generated by `gencorpus.py` with a
fixed random seed. The corpus is ASCII and bit-identical across machines. The
generator deliberately plants `needle` in about 0.1% of lines while excluding
it from its ordinary vocabulary.

The 1 MiB corpus is retained for stable checksums and short sweep times. Its
sub-second executions make `wc` and `grep` less useful for fine-grained timing
comparisons than the larger workloads, but they remain useful flow and string
processing checks.

### Scalar performance changes after this table

The table above predates the scalar-performance work of 2026-08-17/18
(RTA devirtualisation, the true sequential elision, tail-call emission with
`callconv(.c)`, and transient return slots). Two consequences:

- `feart-novpf` now measures a genuine sequential elision. The earlier
  binaries still carried the VPF locals structs, hooks, and fences, so the
  old `speedup` column overstates the benefit of VPF itself.
- The absolute `feart-novpf` times fell substantially. Single timed runs on
  the same machine: `mapHeavy` 33.8s to about 10s, `mandelbrot` 49.6s to
  about 38s, `nqueens` 45.1s to about 35s. The VPF builds also improved:
  `mandelbrot` 3.0s to about 1.2s, with `nqueens` and `mapHeavy` at about
  2.6s and 1.8s.

These spot measurements are single runs, not `hyperfine` sweeps. Rerun
`./run.sh` to regenerate the full table.

### VPF effect

The `feart-novpf` to `feart` comparison is the primary result. Measured
parallelism is mean process user CPU time divided by mean wall-clock time.

| Benchmark | VPF speedup | FeaRT parallelism |
|---|---:|---:|
| `mapLight` | 11.9x | 26.9x |
| `mapHeavy` | 15.7x | 26.2x |
| `mandelbrot` | 16.5x | 24.1x |
| `nqueens` | 14.9x | 25.0x |
| `primes` | 4.2x | 4.4x |
| `wc` | 0.9x | 1.0x |
| `grep` | 1.0x | 1.0x |

VPF is effective where the program exposes splittable divide-and-conquer work
or a splittable flow terminal. `mapLight` shows that this remains true even when
each leaf performs only trivial work. `primes` has less available parallelism,
so its speedup is lower.

`wc` and `grep` use general `.fold` operations. Their fold functions are not
required to be associative, so the runtime deliberately serializes them. Their
results therefore measure the cost of enabling VPF on a sequential workload,
not a missed parallelization opportunity.

### Java comparison

The direct Java comparison mixes different execution profiles. On the four
divide-and-conquer workloads, Java's measured parallelism was 1.01x--1.06x,
while FeaRT used 24x--27x. The `java/feart` values for `mapLight` and `mapHeavy`
are thus parallel FeaRT versus effectively sequential Java, not a scalar
code-generation win.

The more comparable scalar baseline is Java against `feart-novpf`:

| Benchmark | Java | FeaRT sequential elision | FeaRT / Java |
|---|---:|---:|---:|
| `mapLight` | 2.466s | 26.407s | 10.7x slower |
| `mapHeavy` | 2.398s | 33.817s | 14.1x slower |
| `mandelbrot` | 0.812s | 49.550s | 61.0x slower |
| `nqueens` | 2.210s | 45.094s | 20.4x slower |

The scalar performance gap is largest for `mandelbrot`, which is float-heavy
and allocates a `Complex` value during each escape iteration.

On the flow and corpus workloads, Java uses more parallelism than FeaRT
(`primes`: 17.2x versus 4.4x; `wc`: 11.0x versus 1.0x; `grep`: 10.0x versus
1.0x). Java nonetheless finishes first on all three. These rows are useful
end-to-end observations, but they do not isolate either backend's scalar code
generation.

## Limitations

- Results come from one machine and one core-count setting. They are not a
  scaling study or a cross-platform claim.
- The benchmark commands start a new process on every sample. Startup and Java
  JIT warmup are part of the reported wall time, particularly for `wc` and
  `grep`.
- The Java and FeaRT backends may make different parallelization decisions.
  Direct wall-clock ratios do not normalize for CPU consumption or core count.
- The suite covers automatically parallel functional programs, flows, and
  string processing. It does not include hand-written Zig baselines, manual
  granularity tuning, or ports of `msort`, `bfs`, or `delaunay`.

## Reproducing the report

Requirements: a built compiler JAR, Java, Python 3, and `hyperfine` on `PATH`.

```sh
mvn -f ../../compiler package -DskipTests
./run.sh
python3 report.py
```

`run.sh` generates the corpus if it is absent. It accepts `BENCHES`, `WARMUP`,
`MIN_RUNS`, and `JAR` environment variables. For example:

```sh
BENCHES="mapLight nqueens" WARMUP=5 MIN_RUNS=20 ./run.sh
```

Set the CPU governor to `performance` and keep the machine idle for measurements
intended to compare with this report. The runner emits a warning when it cannot
observe that governor.
